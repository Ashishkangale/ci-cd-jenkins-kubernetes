# CI/CD Pipeline with Jenkins, Docker and Kubernetes

## 1. Project Overview

This project implements an automated **Continuous Integration and Continuous Deployment (CI/CD) pipeline** using **GitHub, Jenkins, Docker, Docker Hub, and Kubernetes**.

The pipeline automatically starts when a change is pushed to the configured GitHub repository. Jenkins checks out the source code, validates the project, builds the application, creates a Docker image, pushes the image to Docker Hub, and deploys the application to a Kubernetes cluster.

The deployment process also includes Kubernetes health checks, rollout verification, and rollback handling to provide a reliable and repeatable deployment workflow.

---

## 2. Objectives

The main objectives of this project are:

- Automatically trigger Jenkins when code is pushed to GitHub.
- Build and validate the application automatically.
- Create a Docker image as the build artifact.
- Push the Docker image to Docker Hub.
- Deploy the application to Kubernetes.
- Verify that the Kubernetes deployment completes successfully.
- Use health checks to verify application availability.
- Provide rollback support when deployment fails.
- Keep credentials outside the source code.
- Make the pipeline configurable and maintainable.
- Provide clear documentation and validation procedures.

## 9. Jenkins Pipeline

The CI/CD pipeline is implemented in:

```text
Jenkinsfile
```

The pipeline contains the following major stages:

```text
Checkout
   ↓
Validate
   ↓
Application Build
   ↓
Docker Check
   ↓
Docker Build
   ↓
Docker Push
   ↓
Kubernetes Validation
   ↓
Deploy to Kubernetes
   ↓
Verify Deployment
```

### Pipeline stages

#### 1. Checkout

Jenkins checks out the latest source code from GitHub.

#### 2. Validate

The pipeline verifies that the required application and Kubernetes files exist.

#### 3. Application Build

The Node.js application dependencies are installed.

#### 4. Docker Check

Jenkins verifies that Docker is available and accessible.

#### 5. Docker Build

A Docker image is created using the application Dockerfile.

The image is tagged using the Jenkins build number and Git commit.

#### 6. Docker Push

The generated image is pushed to Docker Hub using Jenkins-managed credentials.

#### 7. Kubernetes Validation

Jenkins verifies connectivity to the configured Kubernetes cluster using a Jenkins-managed kubeconfig credential.

#### 8. Deploy to Kubernetes

The Kubernetes namespace, service, and deployment are applied.

The deployment image is updated to the newly built Docker image.

#### 9. Verify Deployment

Jenkins waits for the Kubernetes rollout to complete successfully.

If the rollout fails, the pipeline handles the deployment failure and performs rollback logic.

## 10. Automatic GitHub Trigger

A GitHub webhook is configured to automatically notify Jenkins when a commit is pushed.

The workflow is:

```text
git push
    ↓
GitHub
    ↓
Webhook
    ↓
Jenkins
    ↓
Pipeline starts automatically
```

This removes the need to manually select **Build Now** for every code change.

For local Jenkins, an ngrok tunnel was used to make the Jenkins webhook endpoint reachable by GitHub.

## 11. Credentials and Security

Credentials are not hard-coded in the Jenkinsfile.

The project uses Jenkins-managed credentials for:

- Docker Hub authentication.
- Kubernetes cluster access.

The pipeline references credentials by Jenkins credential IDs instead of storing passwords, tokens, or private keys in Git.

Sensitive files such as kubeconfig files and secrets are excluded through `.gitignore`.

Example:

```text
kubeconfig
kubeconfig.yaml
credentials/
secrets/
.env
```

The Docker container also runs the application as a non-root user.

## 12. Health Checks

Kubernetes uses two HTTP health checks.

### Readiness Probe

```text
/health
```

The readiness probe determines whether the application is ready to receive traffic.

### Liveness Probe

```text
/health
```

The liveness probe helps Kubernetes identify whether the application is still running correctly.

This improves deployment reliability and helps prevent unhealthy containers from receiving traffic.

## 13. Deployment Verification

After deployment, Jenkins verifies the Kubernetes rollout using:

```bash
kubectl rollout status deployment/cicd-demo -n cicd-demo
```

The deployed pods can also be checked using:

```bash
kubectl get pods -n cicd-demo
```

The deployed image can be verified using:

```bash
kubectl get deployment cicd-demo -n cicd-demo -o jsonpath="{.spec.template.spec.containers[0].image}"
```

---

## 14. Rollback Strategy

The Kubernetes deployment uses a RollingUpdate strategy.

If a deployment needs to be reverted, Kubernetes rollout history can be checked using:

```bash
kubectl rollout history deployment/cicd-demo -n cicd-demo
```

A previous revision can be restored using:

```bash
kubectl rollout undo deployment/cicd-demo -n cicd-demo
```

The rollback can then be verified using:

```bash
kubectl rollout status deployment/cicd-demo -n cicd-demo
```

This provides a mechanism to recover from an unsuccessful deployment.

## 18. Scalability and Adaptability

The pipeline is designed so that it can be adapted for different repositories and Kubernetes environments.

The general workflow can be reused by changing:

- Git repository configuration.
- Docker image repository.
- Kubernetes credentials.
- Kubernetes cluster configuration.
- Application-specific deployment configuration.

Jenkins credentials are separated from the pipeline logic, allowing deployment environments to be changed without placing sensitive information in the source code.

The Kubernetes deployment also uses multiple replicas, resource configuration, health checks, and a rolling update strategy.

---

## 19. Error Handling

The pipeline is designed to stop when an important stage fails.

Examples include:

- Application validation failure.
- Docker build failure.
- Docker push failure.
- Kubernetes connectivity failure.
- Kubernetes deployment failure.
- Rollout timeout or failure.

The pipeline provides stage-level feedback in Jenkins so that the failed operation can be identified.

Deployment rollback logic is also included to help recover from unsuccessful Kubernetes deployments.
